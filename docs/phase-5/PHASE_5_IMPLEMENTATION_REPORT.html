A. Phase 5 Implementation Result

Phase 5 is implemented against the current project.

  • New account / first-time authenticated user runs the existing onboarding question screens (no UI redesign). Every answer is held in OnboardingViewModel.uiState across all screens.
  • On the final question, the answers are assembled into one UserProfile keyed to authRepository.currentUserId() and persisted with a single Supabase upsert to public.profiles.
  • Onboarding completion is now a real onboarding_completed boolean NOT NULL DEFAULT false column, written true only on the success branch of the save. On failure nothing is marked and no forward navigation occurs — the existing error / disabled-button behavior on SkinSensitivityScreen is retained.
  • Returning authenticated users are routed by the actual onboarding_completed value (not by "a row exists"), both at app startup and immediately after authentication.
  • All four onboarding entry paths (manual email signup, email sign-in of an incomplete user, Google auth for a new / incomplete user, restored session with incomplete onboarding) reset OnboardingViewModel and resolve the user's identity before the first question, so stale answers from a previous attempt or another user cannot survive, and the manual-signup full name is never clobbered.
  • The manual-signup full name is preserved and persisted; for Google users the display name is taken from authenticated user metadata (never fabricated) and persisted when present.
  • Home and Profile show the real persisted name instead of the hardcoded "Team 03", loaded through a ProfileRepository read; neutral fallbacks are used when no name is available. Layout / styling / navigation of both screens is unchanged. No profile-photo work (that is Phase 6).
  • Supabase stays entirely under data/. No io.github.jan.supabase import was added to feature/, ui/, or domain/. architectureCheck still passes. AppContainer / ViewModelFactory architecture is preserved (one new ViewModel wired identically to the existing five).
  • No Supabase credentials are hardcoded. No fake persistence or fake success states.
  • Scan / acne model / ONNX / ScanViewModel / ScanScreen / ScanResultScreen / backend / acne tests were not modified.

Verification: architectureCheck, compileDebugKotlin, compileDebugUnitTestKotlin, lintDebug (0 errors), and assembleDebug (APK produced) all succeed. testDebugUnitTest is 33 pass / 1 fail; the one failure is a pre-existing, previously-masked teammate scan test (YoloPostProcessorTest), unrelated to Phase 5 — see sections K and M. D. Exact Database Migration Created and What It Does

supabase/migrations/20260910000000_add_onboarding_completed.sql — timestamp is after the existing 20260909000000_create_profiles.sql, so migration history is additive and nothing is edited destructively.

1. Schema:

alter table public.profiles
    add column if not exists onboarding_completed boolean not null default false;

2. Backfill (deliberately not "mark every existing profile completed"):

update public.profiles
set onboarding_completed = true
where onboarding_completed = false
  and age_range is not null
  and gender is not null
  and is_skin_sensitive is not null;

Choice and rationale: In the shipped app the only writer of age_range, gender, and is_skin_sensitive is the final onboarding save, which writes them together. Their combined presence is therefore reliable evidence that the questionnaire was completed. skin_type is excluded from the condition because the onboarding flow lets the user tap "Skip for now", leaving it legitimately null. Any row missing a required answer keeps the safe default false, so that user is asked the onboarding questions again rather than being silently advanced past onboarding with incomplete data. A false-negative here is harmless (ask once more); a false-positive would strand a user with null answers.

3. RLS: unchanged. Adding a column does not alter existing policies; the per-user SELECT / INSERT / UPDATE policies from the initial migration continue to restrict every row to auth.uid() = id. No new policy is required because onboarding_completed lives on the row the user already owns. The one-time UPDATE runs with migration privileges server-side — never from the client, and never with a service-role key embedded in the Android app.

4. Forward / backward safety: If the app runs before this migration is applied, ProfileRow.onboarding_completed deserializes to its default false (Kotlinx serialization default + Supabase's ignoreUnknownKeys), so nothing crashes and every user is simply treated as "not yet completed" — the safe direction.

E. How Each Onboarding Answer Is Persisted

Answers are collected into the single app-scoped OnboardingViewModel.uiState (OnboardingUiState) as the user moves through the existing screens:

save() builds one UserProfile(id = currentUserId(), fullName, ageRange, skinType, gender, isSkinSensitive, onboardingCompleted = true) and calls profileRepository.saveProfile(...).

SupabaseProfileRepository.saveProfile performs a single client.postgrest["profiles"].upsert(profile.toProfileRow()) — an upsert on primary key id, writing full_name, age_range, skin_type, gender, is_skin_sensitive, onboarding_completed (created_at / updated_at are DB-managed).

On onFailure: errorMessage is set, isSaving = false, saveCompleted stays false, no navigation. On onSuccess: saveCompleted = true, which drives navigation to Welcome → Home.

Data-loss items from the audit are closed: full_name is now populated on every entry path via start(), and completion is an explicit column rather than an inferred one.

F. How the Authenticated Supabase User ID Is Associated with the Profile

OnboardingViewModel.save() calls authRepository.currentUserId() → SupabaseAuthRepository.currentUserId() → client.auth.currentUserOrNull()?.id.

  • If it is null, save() sets errorMessage = "Your session is no longer active." and returns without calling the repository — no persistence.
  • Otherwise that id is UserProfile.id → ProfileRow.id → the upsert's primary key.

The UI layer never supplies, and cannot override, an id — screens only pass answer values through typed callbacks. Server-side, RLS with check ((select auth.uid()) = id) rejects any insert / update whose row id is not the caller's own. ProfileViewModel.refresh() likewise reads authRepository.currentUserId() itself and never accepts an id from a screen.

G. How Onboarding Completion Is Now Determined

SupabaseProfileRepository.hasCompletedOnboarding(userId):

client.postgrest["profiles"]
    .select { filter { eq("id", userId) } }
    .decodeList<ProfileRow>()
    .isOnboardingCompleted()          // firstOrNull()?.onboarding_completed == true

A row that exists with onboarding_completed = false returns false. No row returns false. AuthViewModel.determineDestination() (unchanged) consumes this Result<Boolean> to choose HOME vs ONBOARDING, and it is evaluated both at startup (startupDestination) and on a fresh AUTHENTICATED transition (AuthEvent.SignedIn(destination)). The decision rule is a pure internal function so it is unit-tested directly without a Supabase client.

H. How Manual-Signup and Google Display Names Are Handled

  • Manual email signup: SignUpScreen → AuthViewModel.signUp(fullName, …) → AuthEvent.SignedUp(fullName) → WeGlowApp calls onboardingViewModel.start(event.fullName). The trimmed, validated, non-blank name goes into OnboardingUiState.fullName and is persisted to profiles.full_name by the final save. Supabase email signup writes no user metadata, so the metadata fallback cannot override it. This path is unchanged except that start is now null-safe.
  • Email sign-in of an incomplete user / Google new-or-incomplete user / restored session into onboarding: WeGlowApp now calls onboardingViewModel.start() (no argument) at each of these entries. start() first wipes any prior OnboardingUiState, then resolves the name from authRepository.currentUserDisplayName() → SupabaseAuthRepository reads userMetadata keys full_name → name → user_name → preferred_username, first non-blank wins (Google populates full_name / name). If nothing usable exists, fullName is "" and persists as null.
  • No invented names. The name is only ever a value the user typed at signup or a value the identity provider returned.
  • The resolved name is persisted to profiles.full_name as part of the same successful onboarding upsert.

I. How Home / Profile Obtain the Real User's Name

New ProfileViewModel (constructed in WeGlowApp via the existing viewModelFactory helper from container.authRepository + container.profileRepository; AppContainer needed no change — it already exposes both).

WeGlowApp runs LaunchedEffect(Unit) { profileViewModel.refresh() } when the Home and Profile destinations are entered. refresh():

  1. authRepository.currentUserId() — if null, clears state so the neutral fallback shows.
  2. profileRepository.getProfile(userId) → SupabaseProfileRepository → select … decodeList<ProfileRow>().firstOrNull()?.toUserProfile().
  3. displayName = persistedProfile.fullName?.trim()?.takeIf { it.isNotBlank() } ?: authRepository.currentUserDisplayName()?.trim()?.takeIf { it.isNotBlank() }.

WeGlowApp passes profileState.displayName into HomeScreen(displayName = …) and ProfileScreen(displayName = …).

  • Home: displayName?.let { "Hello, $it" } ?: "Hello there".
  • Profile: displayName ?: "Your Profile".

Both are neutral fallbacks — no fabricated user data. No Supabase import enters feature/ or ui/. Figma layout, spacing, styling, navigation, and other functionality of both screens are untouched. No profile-photo upload (Phase 6).
